# Impact-analysis graph

A queryable dependency graph of the repository. Ask it **"if X changes, what is affected?"** and it lists the affected screens, APIs, classes, topics, tables, deploy files and tests. Every link carries the source line that proves it.

- **Snapshot:** `master` at `64d5abe92` (30 Oct 2026).
- **Size:** 1,044 nodes; 2,488 evidence-backed edges (2,342 confirmed, 146 inferred); 157 derived API → deployable links.
- **Validation:** every evidence line was re-checked against the source tree by `validate.mjs`, with 0 failures.

## How it was built

The graph was built **module by module**, not in a single pass over the whole repository. Five passes each read one part of the code and wrote their findings as JSON to a shared schema ([`SCHEMA.md`](SCHEMA.md)):

| Pass | File | Scope | Edges |
|---|---|---|---|
| pgr-core | `graph/pgr-core.json` | Complaint APIs, services, validators, workflow calls, Kafka, status and SLA logic, workflow definition | 514 |
| pgr-data | `graph/pgr-data.json` | Flyway tables and materialized views, analytics, dashboard, onboarding, persister and indexer mappings | 351 |
| consumers | `graph/consumers.json` | novu-bridge, thin-event contract, NOTIFICATIONS seeds, user-preferences, config-service, xstate-chatbot, digit-mcp, both API endpoint maps | 550 |
| frontends | `graph/frontends.json` | digit-ui-esbuild `products/pgr` and dashboard screens, configurator screens, every test that hard-codes statuses, topics or SLA values | 532 |
| infra | `graph/infra.json` | identity-bff, Keycloak, Kong and nginx routes, Compose, Helm, CI workflows, config-file wiring | 541 |

Each relationship records a file, a line and an exact text match. Each pass self-checked its own output; `validate.mjs` then re-checks the merged graph. Relationships that could not be proven line by line are kept only as `inferred`, with a note.

## Commands

All scripts use Node 20 and have no dependencies. Run them from the repo root.

```bash
# Re-check every relationship against the current source (exit 1 on failure; run in CI)
node knowledge-graph/impact/validate.mjs
node knowledge-graph/impact/validate.mjs --fix-lines   # code moved: update line numbers

# What is affected if X changes?
node knowledge-graph/impact/impact.mjs topic:update-pgr-request
node knowledge-graph/impact/impact.mjs field:Service.applicationStatus --depth 2
node knowledge-graph/impact/impact.mjs service:egov-hrms --confirmed
node knowledge-graph/impact/impact.mjs wf:state:PENDINGATLME,wf:action:ESCALATE --depth 1

# What does X depend on?
node knowledge-graph/impact/impact.mjs class:PGRService --deps --depth 1

# Find node ids
node knowledge-graph/impact/impact.mjs slaHours --list

# Draw it
node knowledge-graph/impact/impact.mjs service:boundary-service --mermaid /tmp/boundary.mmd

# Regenerate the worked scenarios and the layer overview
bash knowledge-graph/impact/scenarios/generate.sh
node knowledge-graph/impact/layers.mjs
```

Options for `impact.mjs`:
- `--depth N` (default 4)
- `--rels a,b` to follow only some relationship types
- `--confirmed` to ignore inferred edges
- `--mermaid FILE`, with `--mermaid-depth N` to draw fewer hops than are reported

The text report shows, for each affected node, the edge that reached it and its `file:line`.

## Reading the graph

- **Direction:** every edge points from the dependent to its dependency, so "if `to` changes, `from` may break". `impact.mjs` walks the edges backwards from the changed node.
- **Node ids:** `prefix:name`. The prefix is the node type and decides its layer:

| Layer | Prefixes |
|---|---|
| 1 · Business | `biz:` concepts, `wf:` workflow states, actions and business service |
| 2 · Application | `screen:`, `api:`, `class:`, `code:`, `config:`, `test:` |
| 3 · Data | `table:`, `field:`, `master:` |
| 4 · Integration | `topic:`, `coreapi:`, `ext:` |
| 5 · Infrastructure | `service:` deployables, `infra:` Compose, Helm, Kong, nginx, CI and config files |

- **Normalizations** applied when loading the graph (`lib.mjs`):
  - `/egov-mdms-service/*` is merged into `/mdms-v2/*`, because `local-setup/nginx/mdms-proxy.conf` rewrites one to the other.
  - Every `api:` and `coreapi:` node gets a **derived** `part-of` link to the deployable that serves its context path. These links have no evidence line; the path rule is the evidence. They let you query a whole DIGIT core service, for example `service:egov-workflow-v2`.

## Worked scenarios

Generated by [`scenarios/generate.sh`](scenarios/generate.sh). Each has a full text report (`.txt`, two hops, every edge with `file:line`) and a ripple diagram (`.mmd`: Changed → 1 hop → 2 hops).

### 1. The complaint status model changes

**Start:** `field:Service.applicationStatus` and all 9 `wf:state:*` nodes. **Result:** 183 affected nodes (17 screens, 31 Java classes, 46 code/config modules, 8 tables or views, 48 tests). Files: [`1-complaint-status-model.txt`](scenarios/1-complaint-status-model.txt), [`.mmd`](scenarios/1-complaint-status-model.mmd).

What has to change together:
- **Workflow definition** in 4 copies: three `PgrWorkflowConfig.json` templates and `platform-baseline-v1.json`, the last loaded by `class:PlatformBaseline`.
- **pgr-services:**
  - `PGRConstants` and the `PGRConfiguration` defaults, such as the unassigned states used by `VisibilityService`
  - `WorkflowService`, which writes `applicationStatus`
  - `PGRQueryBuilder`, whose dynamic data counts `CLOSEDAFTERRESOLUTION`
  - `EscalationService` and `EscalationScheduler`, whose eligible status is `PENDINGATLME`
  - `ThinEventBuilder`
- **Notifications:**
  - the event name is `COMPLAINTS.WORKFLOW.<ACTION>.<STATE>`, so the thin-event contract (`thin-event-v1.schema.json`) and the seeded `NOTIFICATIONS.EventCatalogue`, `Routing` and `Template` all embed state names
  - novu-bridge routes on the exact event-name string, so a renamed state with stale seeds is rejected and sent to the DLQ
- **Analytics SQL:** `complaint_facts` hard-codes `RESOLVED`, `REJECTED` and `CLOSEDAFTER*`. `pgr_mv_kpi` and `pgr_mv_dimension` read the column directly.
- **Persister and indexer:** both persister mappings write the column; the inbox indexer reads it (inferred).
- **UI:**
  - digit-ui: inbox, details, timeline instances, `TimeLine.js` (including the UI-only `PENDINGFORASSIGNMENT_AFTERREOPEN` case), `UICustomizations.js`, `citizenComplaints.js`, and the dashboard presentation configs
  - configurator: `StatusChip`, `WorkflowActionSelect`, notification save guard, weekly report
  - chatbot: status-update messages
  - digit-mcp: `pgr-workflow.ts`, `formatter.ts`, dashboard seeds
- **Tests:** 48 test files hard-code state names, including `PGRServiceTest`, `ThinEventBuilderTest`, the escalation tests and the Playwright lifecycle and inbox specs.

### 4. The SLA calculation changes

**Start:** `field:ComplaintHierarchy.slaHours`, `config:pgr.business.level.sla`, `config:pgr.escalation.default.sla.ms`, `master:RAINMAKER-PGR.EscalationConfig` (and its ladder and override fields), `field:BusinessService.businessServiceSla`. **Result:** 81 affected nodes. Files: [`4-sla-calculation.txt`](scenarios/4-sla-calculation.txt), [`.mmd`](scenarios/4-sla-calculation.mmd).

The SLA is computed **independently in five places**. All of them must change together:

| # | Where | How |
|---|---|---|
| 1 | pgr-services `MDMSUtils#getServiceCodeToSlaMillis` + `PGRQueryBuilder` | `sortBy=sla` ordering with `pgr.business.level.sla` fallback |
| 2 | `EscalationConfigurationService` + `EscalationService` | Escalation ladder: EscalationConfig percentages of `slaHours`, clock from `createdTime` |
| 3 | Flyway SQL for `complaint_facts` | `sla_target_ms` / `sla_breached` = slaHours, else EscalationConfig, else workflow `businessServiceSla` |
| 4 | `configs/egov-indexer/pgr-services.yml` | `Data.slaHours` enrichment on create only |
| 5 | digit-ui `products/pgr` `usePGRInboxSearch` + `utils/index.js` | Inbox "days remaining" computed in the browser, with a hard-coded `DEFAULT_SLA_MS = 432000000` copy of the backend default |

The values are written by configurator `ComplaintTypeEdit`/`Create`/`List`, the onboarding `ComplaintsStep` (default 72 h, while the backend default is 5 days), `ComplaintHierarchySetup` and the `EscalationPolicyEditor`. 17 tests hard-code SLA values.

## Keeping it current

- **Run `validate.mjs` in CI.** If a referenced line is deleted or its text changes, the edge fails, so the graph cannot silently go out of date. `--fix-lines` absorbs code that only moved.
- **When a module changes,** update only that module's `graph/<module>.json`. The schema is in [`SCHEMA.md`](SCHEMA.md); the evidence rule is a short exact substring on one line that proves the relationship.
- **Then regenerate** with `scenarios/generate.sh` and `layers.mjs`.
