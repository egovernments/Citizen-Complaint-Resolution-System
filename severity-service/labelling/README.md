# Labelling

Everything needed to define, run and check severity labelling for the cleaned complaint data:

- `rubric.json` is the single source of truth for what Low / Medium / High / Critical mean (currently **v0.3**).
- `prompts/system.md` is generated from it by `build_prompt.py` (`--check` verifies it is current); `prompts/user.md` is a single-complaint answer template kept for manual use; the batch engine (`llm_label.py`) does not read it and builds its own batch instruction (a JSON list in, a JSON array out).
- `llm_label.py` labels complaints with a free-tier LLM API, in resumable batches (the labelling engine).
- `pipeline.py` wraps it so labelling can be repeated and improved in small steps: runs with records, targeted reruns, human review and promotion (see [Iterating](#iterating-on-the-labels)).
- `colab_llm_labelling.ipynb` (generated by `make_colab_notebook.py`) runs the same thing as a notebook, locally or on Colab.
- `export_sample_csv.py` builds the reviewable CSV for the random 2,000-complaint sample.

> **Status (2026-11-08):** all 58,640 cleaned complaints now have an LLM severity label in `output/llm_labels.csv`. These are **LLM opinions, not verified ground truth** (see [Caveats](#caveats)). The evaluation set must still be labelled by people (see [Human labelling process](#human-labelling-process-evaluation-set)).

## Iterating on the labels

Labelling is meant to be repeated: change the rubric, relabel only what needs it, let people correct the doubtful cases, and promote the result. `pipeline.py` keeps each step recorded so any two passes can be compared.

```
 rubric.json  ->  build_prompt.py  ->  pipeline.py label   ->  runs/<run_id>/   (one model, one rubric version per run)
      ^                                     |                        |
      |                               report / compare         review-export  ->  people fill reviewed_label
      |                                     |                        |
      +------ change rules <---------- look at disagreements        v
                                                          promote  ->  output/llm_labels.csv  ->  training/
```

**Concepts**

| Term | Meaning |
| --- | --- |
| Run | One labelling pass under `runs/<run_id>/`, made with one model and one rubric version. Holds `labels.csv`, `manifest.json` (rubric version, prompt hash, model, settings, counts, commands) and `report.json` (distribution and agreement with the source labels). |
| Stale | A run whose prompt hash differs from the current `prompts/system.md`, i.e. the rubric changed after it was made. `status` flags these. |
| Overlay | A later run that redoes only some rows (for example the unclear ones). Its labels replace the base run's labels for those rows. |
| Review | A CSV of rows for people to decide. Their `reviewed_label` beats every model label. |
| Promoted labels | `output/llm_labels.csv`: the labels used for training, built from a base run, overlays and reviews. Every row has a `label_source` (a run id, or `human`), and `output/llm_labels.manifest.json` records how it was built. |

**The loop**

```bash
python labelling/pipeline.py status                                   # runs, stale or current, what is promoted

# 1. label everything with the current rubric (resumable; rerun the same command to continue)
python labelling/pipeline.py label --run-id r2 --model gemini-3.1-flash-lite --batch-size 100

# 2. measure it, and compare with an earlier run
python labelling/pipeline.py report  r2
python labelling/pipeline.py compare run-001-initial r2               # agreement, confusion table, differing rows CSV

# 3. redo only part of it: the rows a run flagged unclear, or where it disagrees with the source labels / another run
python labelling/pipeline.py label --run-id r2-redo --model gemini-3.1-flash-lite --select unclear --base-run r2

# 4. let people check the doubtful rows
python labelling/pipeline.py review-export --run r2 --select disagree-source --limit 300   # -> review/r2_disagree-source.csv
#    fill the reviewed_label column (Low / Medium / High / Critical), save the file

# 5. build the label file used for training
python labelling/pipeline.py promote r2 --overlay r2-redo --reviews labelling/review/r2_disagree-source.csv
```

**Rules that keep iterations comparable**
- **One model and one rubric version per run.** Changing the model or the rubric needs a new run id; the tool refuses to continue a run if the prompt changed.
- **After editing `rubric.json`:** bump `version`, run `build_prompt.py`, then `status` shows every earlier run as stale. Start a new run (or an overlay for just the affected rows).
- **Parallel labelling:** use different row ranges and API keys in the same run, for example `--start 0 --end 20000 --key-env KEY_A` in one terminal and `--start 20000 --key-env KEY_B` in another. Each range writes its own part file; `report`/`promote` merge them.
- **Targeted rerun selections:** `unclear`, `disagree-source`, `disagree-with:<other run>`.
- **Promotion refuses incomplete labels** unless `--allow-partial` is given, so training never silently uses half a dataset.
- **Review files** are read with or without an Excel byte-order mark; any invalid `reviewed_label` stops the promotion with the offending row.
- **What is kept in git:** each run's `manifest.json` and `report.json`, the review CSVs, the promoted labels and their manifest. The (large) per-run label files stay local; `register` records labels made outside the pipeline (this is how `run-001-initial` was added).

After promoting, retrain with `training/` (see `training/README.md`) and compare `metrics.json` with the previous model before replacing `model/`.

**Review of how the existing labels relate to complaint themes** (keyword rates and read-through samples per level). The key finding was that the existing labels are internally inconsistent on several themes, so the rubric could not simply copy them:

- Accident / injury wording appears in about 50% of Critical rows but only 2-6% of the other levels.
- Dog-bite / rabies wording: about 19% of Critical, about 4% of High, about 1% of Medium.
- Stagnation / drain-overflow wording is about 30% of High but under 3% of Medium and Low.
- Encroachment / illegal / unauthorised / parking / tax wording is concentrated in Low (about 40% of Low rows).
- But "street light not burning" and "garbage not cleared for days" appear in every level, and dog complaints are spread over Critical, High and Medium.
- Cleaning had already found 523 groups of identical texts with conflicting labels (43,328 rows), another sign of label noise.

## 3. The rubric (v0.3)

`rubric.json` has: principles, ordered decision rules, four levels (each with meaning, criteria and example complaints) and open items. History:

- **v0.1** (draft before looking at the data): Critical needed actual or imminent injury; dog threats were High; encroachment and potholes were higher than the data supports.
- **v0.2**: first alignment to the labels' themes (accident risk and dog bites to Critical, encroachment to Low, and so on).
- **v0.3** (current): a consistent rubric with explicit decision rules, not a copy of the noisy labels. Main rules:
  - **Dogs:** bite, attack, chase or rabies = Critical; a pack that makes the street unsafe for children or the elderly, with no bite = High; merely present or noisy = Medium; sterilisation or feeding queries = Low.
  - **Open hazards:** uncovered manhole, drain, pit or dug-up road someone could fall into, or a fallen or about-to-fall tree or pole = Critical; broken or missing cover with nobody at risk = High.
  - **Water:** stagnation, drain or sewage overflow or leak = High; sewage in a house or drinking water = Critical; desilting needed but nothing standing = Medium.
  - **Road damage:** Medium by default; High if a main route is badly broken; Critical if people are falling or being injured.
  - **Street lights:** not burning = Medium; sparking, shocks, exposed wiring or leaning = Critical; request for a new light = Low.
  - **Garbage:** Medium by default; High if it causes smell, pests, a blocked drain or is left many days; burning waste that threatens people = Critical.
  - **Cattle**, **rules and requests** (encroachment, illegal construction, unauthorised boards, tax queries are Low unless a safety hazard is described) and **system messages or thanks** (Low, unclear).
  - Principles include: judge the text only, urgent words alone do not raise the level, repeated reports do not raise the level, judge by meaning for Tamil or mixed language, near ties go to the lower level with `unclear = true`.

`prompts/system.md` is generated from the rubric (principles, decision rules, levels with criteria and examples).

## 4. The labelling tool (`llm_label.py`)

Design:

- **Batching:** many complaints per request (JSON list in, JSON array out) to stay inside free-tier request limits. The model returns, per complaint: `id`, `severity` (enum), `unclear` (bool) and a short `reason`. Gemini uses a response schema; Groq uses JSON mode with a `{"results": [...]}` wrapper.
- **Resumable:** results are appended after every batch; ids already present in the output are skipped, so a stopped or failed run just continues when started again.
- **Robust:** retries on rate limits (honours the server's retry delay), 5xx errors and dropped connections; stops cleanly with a message when a daily quota is exhausted. Complaint text is treated as data, never as instructions.
- **Options:** `--provider gemini|groq`, `--model`, `--batch-size`, `--rpm`, `--limit N` (first N rows), `--sample N` (seeded random N), `--start/--end` (row positions, for splitting work), `--output`, `--key-env` (which environment variable holds the key), `--also-done FILES` (treat ids in other files as already done), `--list-models`, `--dry-run`.
- **Keys** are read from `labelling/.env` (git-ignored; see `.env.example`). Never commit keys.
- Standard library only (no installs).

**Provider limits observed** (free tier, these change; check the provider):

| Provider / model | Limit seen | Effect |
| --- | --- | --- |
| Gemini (free tier) | 500 requests per day per project per model (error text said so) | About 80-100 complaints per request is what makes 58k feasible |
| Gemini `gemini-2.5-flash-lite` | "no longer available to new users" | Switched to `gemini-3.5-flash-lite`, later `gemini-3.1-flash-lite` (quota is per model, so a second model has its own allowance) |
| Groq `openai/gpt-oss-120b` | 1,000 requests per day, 8,000 tokens per minute (from response headers) | The ~2,000-token rubric is resent each request, so only about 30 complaints per request at one request a minute; roughly 22 hours for the remainder. The Llama models were not available on the key. |

## 5. Experiments and what they showed

1. **First pilot was invalid.** The first 500 rows were all Critical because the file is sorted by label. Fix: `--sample` draws a seeded random subset.
2. **Random 500 (Gemini 3.5 flash-lite):** 61.6% exact agreement with the existing labels.
3. **Groq test (90 random):** 54.5% exact agreement (88 labelled, 2 failed and would be retried). On about 350 rows of the random 2,000 it agreed with the source 55% and with Gemini 74%. Groq was also far slower, so it was not used for the main run beyond a few hundred rows.
4. **Random 2,000 (Gemini 3.1 flash-lite)**: the fairest measurement. Agreement with the existing (source) labels:

| Metric | Value |
| --- | --- |
| Exact match (agreement, not true accuracy) | **62.2%** (mismatch 37.8%) |
| Within one level | 93.7% (off by 1 / 2 / 3 levels: 31.5% / 5.4% / 1.0%) |
| Gemini higher / lower than source | 19.2% / 18.6% (no systematic direction) |
| Cohen's kappa / weighted kappa | 0.464 / 0.626 |
| Macro F1 | 60.0% |
| Marked `unclear` | 3.5% |

| Level | Source n | Gemini n | Recall | Precision | F1 |
| --- | --- | --- | --- | --- | --- |
| Low | 490 | 471 | 70.0% | 72.8% | 71.4% |
| Medium | 699 | 784 | 62.4% | 55.6% | 58.8% |
| High | 683 | 547 | 57.0% | 71.1% | 63.3% |
| Critical | 128 | 198 | 59.4% | 38.4% | 46.6% |

Confusion matrix (rows = source label, columns = Gemini label):

| | Low | Medium | High | Critical |
| --- | --- | --- | --- | --- |
| Low | 343 | 123 | 14 | 10 |
| Medium | 94 | 436 | 124 | 45 |
| High | 25 | 202 | 389 | 67 |
| Critical | 9 | 23 | 20 | 76 |

Reading: moderate agreement; disagreements are mostly one level apart and balanced in both directions. Gemini flags more Critical than the source (198 vs 128), so Critical precision is low. About 30% of source-High complaints are labelled Medium by Gemini. Which side is "right" is not known; neither set of labels has been double-checked by people.

`output/sample2000_gemini_labels.csv` (committed) has the 2,000 complaints with the source label, Gemini label, reason and a match flag, for reading disagreements.

## 8. Problems met and how they were fixed

| Problem | Cause | Fix |
| --- | --- | --- |
| `git pull` blocked, "unlink failed" | Excel held the old CSV open (Windows) | Extracted the remote CSV via `git show`; reset the branch pointer without touching files; swap the CSV in once Excel is closed |
| Pilot looked all-Critical | File sorted by label | `--sample` seeded random subset |
| 404 "model no longer available" | `gemini-2.5-flash-lite` closed to new users | Use `gemini-3.5-flash-lite` / `gemini-3.1-flash-lite` (`--list-models` shows what the key can use) |
| Crash `RemoteDisconnected` | Server closed a connection; the retry handler did not catch it | Retry on all network/connection errors |
| DNS error `getaddrinfo failed` | Local internet drop, not a quota problem | Retries; rerun resumes |
| Many duplicate rows, quota burned fast | Re-running the notebook after a disconnect left the old copy running (seven copies at once, all appending to one file) | Stop all copies, de-duplicate keeping the first row per id; **only ever run one copy per output file** |
| 401 from Groq | An xAI (`xai-...`) key was pasted instead of a Groq (`gsk_...`) key | Use the key from console.groq.com |
| `%%writefile` failed in Colab | It does not create folders | Notebook creates the folders first |
| Groq too slow | 8,000 tokens/minute free limit and the rubric resent every request | Used Gemini for the bulk of the work |
| Gemini daily quota hit | 500 requests per day per project per model | Larger batches (80-100); a different Gemini model has its own quota; parallel ranges |

## 9. Caveats

- **Not ground truth.** The LLM labels agree with the existing labels about 60%; neither set has been checked by people. Agreement is not accuracy.
- **Mixed labellers.** The final file mixes Gemini 3.5 flash-lite (first ~19k), Gemini 3.1 flash-lite (most of the rest) and a few hundred Groq labels; the model used per row was not recorded.
- **The LLM is stricter on Critical** than the existing labels (6,142 vs 4,275 Critical).
- **Rubric judgement calls** (dogs, potholes, garbage, street lights) are where the labels disagree most; these need review by someone who handles real complaints.
- **Manifest hash:** the `output_sha256` in `data/complaints_description_only_cleaned.manifest.json` does not match the committed CSV's SHA-256 (with LF or CRLF endings); worth checking with whoever generated it.

## 10. Reproduce

The iterative way is `pipeline.py` (see [Iterating](#iterating-on-the-labels)). The direct commands below call the labelling engine itself.

```bash
# from the repo root; key goes in severity-service/labelling/.env (see .env.example)
python severity-service/labelling/build_prompt.py --check        # prompt matches rubric
python severity-service/labelling/llm_label.py --list-models     # check key and model names
python severity-service/labelling/llm_label.py --provider gemini --model gemini-3.1-flash-lite --sample 2000 --output severity-service/labelling/output/sample2000_gemini31.csv
python severity-service/labelling/export_sample_csv.py           # builds output/sample2000_gemini_labels.csv
# full run (resumable; run ONE copy per output file). Split work with --start/--end:
python severity-service/labelling/llm_label.py --provider gemini --model gemini-3.1-flash-lite --batch-size 100 --start 0 --end 40000
python severity-service/labelling/llm_label.py --provider gemini --model gemini-3.1-flash-lite --batch-size 100 --start 40000 --output severity-service/labelling/output/llm_labels_part2.csv --key-env GEMINI_API_KEY_2 --also-done severity-service/labelling/output/llm_labels.csv
```

The notebook `colab_llm_labelling.ipynb` does the same (pilot, comparison chart, full run, results). Regenerate it after changing the script with `python labelling/make_colab_notebook.py`.

## 11. Suggested next steps

- Check how reliable the existing labels are before training: people read a sample of the disagreements (filter `matches_source = False` in `sample2000_gemini_labels.csv`), concentrating on High vs Medium and Critical vs High.
- The first model can be trained on the existing source labels (complete for all rows) with the LLM labels as a second opinion, or on the LLM labels; decide after the review above.
- Evaluation must use an independently, human-labelled set (next section), never the LLM labels used for training.

## Human labelling process (evaluation set)

For the severity **evaluation set** (about 2,000 complaints):

1. Draw a random sample from `data/complaints_description_only_cleaned.csv`, where PII is already removed and duplicates are dropped (see `data/README.md`).
2. Two people label each complaint independently, using only `rubric.json`. Neither sees the other's label, the existing label or the model's prediction.
3. Disagreements are resolved by a third reviewer, and the final label is recorded along with both original labels.
4. Report accuracy and Critical recall against the model, and annotator agreement (Cohen's kappa) between the two labellers.

Label file format (CSV, one row per complaint):

| Column | Meaning |
| --- | --- |
| `complaint_id` | Id of the complaint |
| `description` | Cleaned complaint text (the only model input) |
| `label_a`, `label_b` | The two independent labels |
| `final_label` | Agreed label (Low / Medium / High / Critical) |
| `notes` | Optional free text on borderline cases |

## Changing the rules

Edit `rubric.json`, bump `version` in it and in `prompts/VERSION`, then run `python labelling/build_prompt.py` (and `python labelling/make_colab_notebook.py` to refresh the notebook).
Do not relabel items already labelled under an earlier version without recording that.
